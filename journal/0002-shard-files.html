0002: The executor writes shard files

2026-11-25 · Done, not reviewed

The owner approved this step before it started.

Goal of this step

Make the code match the decision in entry 0000: the dataset is stored as NumPy shard files. Before this step, the executor wrote JSON.

What was done

FileChange
shard.pyNew. It writes a list of traces to a shard and reads one back. It can also export traces to JSON.
executor.pyIt now writes a shard. It also stores vertex positions with no rounding.
traces.npzNew. The 20 sample traces as a shard.
traces.jsonNow an export made from the shard. The browser player and the frame images still read JSON.
.gitignoreNew. It keeps Python's cache folder out of git.

How the pieces connect now:

  1. The executor runs moves and writes a shard.
  2. The shard is the stored dataset. Training will read it directly.
  3. For viewing, shard.py exports a few traces to JSON.
  4. The player and render.py read that JSON.

Two choices made inside the format

  • Vertex positions are stored as 32-bit numbers. Blender holds positions at that size, so nothing is lost.
  • Move amounts are stored as 64-bit numbers. A rounded amount could rebuild a slightly different mesh, and then the stored example could not be verified.

What we saw

CheckResult

Write the same shard in two separate Blender runsByte-identical files, same SHA-1
Export the new shard to JSON and compare with the JSON from entry 0001Identical. All 20 traces match.
Size of the 20 sample traces4.6 KB as a shard, against 38 KB as JSON
Size of 2,000 traces179 KB, which is about 90 bytes per trace

The replay check is stronger than the one in entry 0001. That one compared two runs in memory. This one reads the file from disk first, so it tests the file format as well as the executor.

What it means

  • The stored format is proven for the plain case. Meshes and moves survive the trip to disk and back with nothing lost.
  • Product scale looks cheap for short traces. At 90 bytes each, a million traces of 1 to 5 moves is about 90 MB. Longer builds and attributes will cost more.

Not done

  • No attributes. The shard holds no UVs, colors, material ids or smooth flags yet. The trial moves do not produce any.
  • No per-trace extras. Origin, quality flags and executor version are not stored yet.
  • One shard only. Nothing splits a large dataset across many shards yet.
  • The reader is slow. It unpacks a whole shard into Python lists. Training will need to slice the arrays directly.

Open questions

  • How many traces go in one shard?
  • Where do origin, quality flags and executor version live?
